A/B Testing compares your current agent, the **Control**, with one or more **Variants** using live calls. Phonely routes the configured share of calls to each variant and evaluates every arm against the same success criterion. Tests can run on the calls your agent answers, on the calls it places, or on both.

Use [Unit Testing](/testing/simulation-testing) for repeatable generated scenarios before exposing changes to live traffic.

## Create a test

Open **Testing > A/B Testing** and create a test in **Planned**. The setup has four parts:

| Step | What you configure |
| --- | --- |
| Test details | Name, description, the category of change, and which calls the test runs on |
| End criteria | Stop after a number of calls or a number of days |
| Traffic split | The percentage of calls sent to the variant, from 1% to 100% in 1% steps; the remainder stays with the control |
| Success criteria | The call outcome, ended reason, or call-duration direction that counts as success |

The category—**Voice**, **Workflow**, **Agent Settings**, **Knowledge Base**, or **Other**—labels what you intend to compare. It does not restrict which variant settings you can edit.

### Choose which calls the test runs on

A **Workflow** test asks which calls it should run on. Choose one:

| Choice | What it splits |
| --- | --- |
| **Inbound calls** | The calls your agent answers |
| **Outbound calls** | The calls placed by campaigns and the API |

Every other category splits calls in both directions, as do workflow tests created before this choice existed.

When a test includes outbound calls, use **Include voicemail calls in results** to decide whether outbound calls that reach voicemail count toward the result. It is off by default, so those calls are excluded until you enable it.

Success-criteria options follow that choice for workflow tests: outcome tags come from the selected direction's calls only, and an inbound test does not offer the **Voicemail** ended reason.

When choosing successful outcomes or ended reasons, search to narrow the options. **Select all N results** selects the matching options and keeps any selections outside the search. If all matches are already selected, selecting it again clears only those matches. Clear the search and review the full selection before starting the test.

### Edit the variant

Make the change you want to measure on the variant, then keep unrelated settings aligned so the result remains interpretable. The **Edit variant** action names the variant's letter once the test has started—for example **Edit Variant C**—and reads plainly for a planned test, which has no letter yet.

How the variant opens depends on the test:

- A delta test (one with no separately copied variant agent) is edited on the **base agent's own page** in Variant B mode. A strip at the top of the window names the test being edited and offers **Back to test**, **Exit to base**, and, once the test has started, **Promote B**. The sidebar, page, and flow editor sit below the strip so it never covers anything. Every surface shows the base agent with the variant's changes applied, and any field, guideline section, or block the variant changes carries a **B** marker; hovering it shows "Changed in Variant B". Saves in this mode go to the variant only, never to the base agent. Some things the variant cannot change—such as phone numbers, compliance, analytics, renaming or deleting the agent, adding or removing flows, and knowledge-base document and website edits—are read-only or refused with a message. Deleting a knowledge-base document or website in Variant B mode drops it from the variant only; the base keeps it.
- A test with its own copied variant agent opens that agent's page in test-agent mode, with the same strip and **Back to test**.
- An outbound workflow test opens the variant's call flow instead. **Edit variant flow** takes you to the campaign page's call-flow canvas, where the Campaigns view is hidden and a chip marks the surface as the variant.

**Promote B** writes only the variant's changes onto the base agent through the published-change path, keeping any base edits made during the test. Publishing a flow on an agent that has a delta test whose variant also changes the same flow asks you first, so you can keep the variant's version while the rest of the change reaches it.

## Start and manage the test

Review the variant before selecting **Begin Test**. While a test is in progress, eligible calls are assigned to the Control or a Variant according to the traffic split.

### Run several tests on one agent

Up to four A/B tests can run on the same agent at once. They share a single control, **A (original)**, and each running test's variant takes its own percentage of the agent's calls. When a test starts, it is assigned the next free letter—**B**, **C**, **D**, or **E**—and keeps that letter after it ends. A planned test shows **Variant** with no letter until it starts, because the letter it would receive can change before then. These letters label the variant everywhere it appears in the app; a planned test can still be edited, but it does not take any calls until you start it.

When you start a test, the **Start test** dialog shows the agent's whole split: A (original), each already-running test's variant, and this test's variant with the letter it will get. Set this test's share up to what A still has; already-running tests keep their shares here, and a running test's percentage is changed from its own test settings.

If the percentage you planned no longer fits beside the running tests, the dialog starts the new test at whatever A has left, and **Make room** previews an even split that gives A and every variant—including the new one—an equal share, with A keeping any percentage that does not divide evenly. When four tests are already running, or no variant letter is free, the agent is at capacity and a new test cannot start until one finishes.

The test appears in one of three sections:

- **Planned** has been configured but is not routing calls.
- **In Progress** is currently routing live calls.
- **Completed** has reached its end criterion or was terminated.

Completed tests open newest first in the table view; use the column headers to change the sort order.

You can adjust the traffic split while a test is in progress. Terminating a test stops new calls from being assigned to it; it does not undo calls already completed.

<Warning>
  A/B Testing affects live traffic. Test the variant independently and begin with a traffic share appropriate for the risk of the change.
</Warning>

## Review the result

Open a test to compare completed calls, successful calls, and success rates for the Control and Variant. You can also open the calls assigned to either arm and inspect them in Call History.

Phonely calculates success from the criterion selected during setup:

- **Call Outcome** counts calls with one of the selected outcomes.
- **Call Ended Reason** counts calls with one of the selected ended reasons.
- **Call Duration** compares whether shorter or longer calls better match the goal.

The result may also show the difference between success rates, the probability that the variant wins, a p-value, and a confidence interval. Success rates and differences are shown to up to three significant digits without rounding up, while the underlying comparisons keep full precision. Treat these as evidence from the calls collected so far, not a guarantee about future calls. A small sample or an interval that crosses zero means the result remains uncertain.

If you decide to keep the variant, apply it deliberately and complete an end-to-end test of the resulting control agent. Do not assume every variant difference should be promoted simply because one metric improved.

<AccordionGroup>
  <Accordion title="The test has few or uneven calls">
    Confirm that the agent is receiving eligible live calls and review the configured traffic split. Random assignment can be uneven in a small sample; allow enough calls before interpreting the result.
  </Accordion>
  <Accordion title="Calls are not counted as successful">
    Review the selected success criterion and the affected calls. Confirm that their outcome, ended reason, or duration matches the values configured for the test.
  </Accordion>
  <Accordion title="The result does not identify a clear winner">
    Review the completed-call count and confidence interval. Continue the test when appropriate, or conclude that the measured change did not produce a reliable difference within the collected sample.
  </Accordion>
</AccordionGroup>
