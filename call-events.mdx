The call events page is where you troubleshoot what happened behind the scenes during your calls. While the calls view shows the conversation outcome (for example, Customer Ended Call or Greeting Hangup), Call Events shows the technical actions executed during the call, such as an API Request, whether it succeeded, what status code it returned, and how long it took.

This is especially useful when you are building workflows that use actions like **API Request**, **Code**, or other event-driven steps and you want to confirm that everything is running as expected.

After you open your call history page, you can switch into the events-level view from the top-right controls.

1. Open the **Calls History** page in your workspace.
2. In the top-right section of the page, locate the view toggle/button labeled **Events**.
3. Use **Refresh** to load the latest event data before starting your review.

## What you can do from this page

The call events page helps you move beyond the final call outcome and inspect what actually happened during execution.

For example, you can use it to:

- confirm whether an action ran successfully
- identify failed workflow actions
- review events by **Pre Call**, **Live Call**, or **Post Call**
- find slow events using execution time
- inspect specific events tied to one **Call ID**
- review integration behavior
- inspect code block input and output
- understand transfer and telephony behavior step by step

In short, this page is your event-level debugging and monitoring workspace.

The page is split into two main working areas: a **filter sidebar** on the left and an **events table** on the right. There are also controls at the top-right for refreshing results, customizing filters, and switching views.

## Understanding event types

Call Events is not limited to API requests. It captures multiple types of system-level actions that occur during a call, giving you full visibility into how your workflow executed behind the scenes.

Common event types include:

- **Telephony** – Actions related to call handling, such as dialing, connecting, transferring, or ending a call.
- **API Request** – Outbound or inbound requests to external systems, including status codes, response times, and success or failure details.
- **Code** – Execution of custom code blocks within your workflow, useful for debugging logic or data transformations.
- **Block Change** – Movement between workflow blocks, helping you trace the exact path the call followed.
- **State Change** – Updates to variables or session state that influence how the flow progresses.

Each event type represents a different layer of your workflow’s behavior, allowing you to troubleshoot issues, validate logic, and confirm that every part of the system is working as expected.

### Telephony events

Telephony events record activity handled directly by the call system, including how the call was connected, routed, transferred, or ended. These events help you understand what occurred at the infrastructure level during the conversation.

They are especially useful when troubleshooting call routing issues, investigating unexpected disconnections, or verifying whether a transfer was successfully completed.

Common examples of telephony event names include:

- End call beginning
- Transfer failed
- Silence timeout activated
- Participant left conference room
- Participant entered conferencerRoom
- Started outbound leg transfer process
- Outbound leg dialed out
- Conference room started
- Transfer call started
- IVR detected
- User entered call

Use these events when you want to troubleshoot:

- transfers that failed
- silence timeout behavior
- IVR detection
- conference room behavior
- outbound leg dialing
- end-call handling
- participant join/leave activity

These events are especially valuable for debugging warm transfer, cold transfer, hold behavior, and call lifecycle issues.

### API Request Events

API Request events give you visibility into outbound calls your workflow makes to external systems. They allow you to confirm whether a request was sent successfully, how long it took, and what response was returned.

For each API Request event, the table and detail view can include information such as:

- **Status** – Indicates whether the request succeeded or failed.
- **Method** – The HTTP method used (for example, GET, POST, PUT, or DELETE).
- **Execution Stage** – Shows whether the request is starting, in progress, or completed.
- **Execution Time** – The total time taken for the request to execute.
- **Request URL** – The endpoint that was called.
- **Response Code** – The HTTP status code returned by the external service.
- **API Response Body** – The payload returned in the response.

These details make it easier to diagnose integration issues, validate external data exchanges, and ensure your workflow is communicating correctly with third-party systems.

These events are useful when you need to confirm:

- whether a request was sent
- whether it succeeded or failed
- what HTTP method was used
- which endpoint was called
- what response code was returned
- what payload came back
- how long the request took

## Code events

Code events give you visibility into what happened inside a code block during execution. They allow you to inspect how inputs were processed, how long the logic ran, and what output was produced. 

The event detail panel typically includes:

- **Event Type** – Identifies the action as a code execution.
- **Execution Stage** – Indicates whether the code is starting, running, or completed.
- **Execution Time** – Shows how long the code block took to run.
- **Code Block Input** – Displays the data passed into the code block.
- **Input** – The evaluated variables or payload at runtime.
- **Code Block Output** – The result returned after the logic was executed.

This makes the events page especially valuable when working with custom logic, calculations, or data transformations, as it allows you to trace issues precisely and confirm that your workflow behaves as intended.

Use these events when you want to inspect:

- What inputs were passed into the code block
- What code ran
- What output the code returned
- Whether the code succeeded
- How long the code execution took

## View Event Details

After reviewing events in the table, you can click any event row to open a detailed side panel with full execution information.

1. Go to the **Call Events** page.
2. Use filters (optional) to narrow down the events you want to inspect.
3. In the **events table**, click the row for the event you want to review.
4. An **Event Details** panel opens on the right side of the page.

This is especially useful when you want to inspect:

- What exactly happened during an event
- Whether an action succeeded or failed
- The execution stage (Pre Call, Live Call, Post Call)
- Request/response details for API events
- Timing and status information for troubleshooting

This panel lets you inspect the selected event without leaving the events page.

## Event Details panel

The event details panel provides a full breakdown of the selected event. Depending on the event type (for example, **API Request**), the fields shown may vary.

These fields help identify and trace the event:

- **Event ID:** A unique identifier for the specific event record.
- **Call ID:** The unique ID of the call this event belongs to.\
  Useful when correlating multiple events from the same call.
- **Workflow ID:** The workflow associated with the event execution.
- **Event Type:** The type of event that occurred (for example, **API Request**).
- **Success:** Indicates whether the event completed successfully (`true` / `false`).
- **Execution Stage:** Shows when the event happened in the call lifecycle, such as **Pre Call, Live Call, or Post Call.**

### Timing and performance details

These fields help you understand event timing and responsiveness:

- **Event Started:** Timestamp for when the event began.
- **Event Ended:** Timestamp for when the event completed.
- **Execution Time:** Total time taken to execute the event (for example, `41.70ms`

This is particularly helpful for diagnosing slow actions or identifying latency in external integrations.

## Customize the Events Table

The column/options menu (opened from the icon next to Refresh) lets you control what fields are available on the page and in what order they appear. This makes the Events page easier to use when you want to focus on a specific troubleshooting workflow.

Use this menu to:

- **Search** for a field/option quickly
- **Show or hide** columns using checkboxes
- **Reorder** fields using drag handles

This is especially useful when you want to prioritize fields like Call ID, Execution Stage, or Execution Time without scrolling through a long filter panel.

1. Go to the **Events** page.
2. Click the customization / columns icon (next to Refresh).
3. The options panel opens with:
   - a search options... bar at the top,
   - a list of available fields,
   - checkboxes to enable/disable each field,
   - and drag handles for reordering.

  ![Selectandsearchcolumns](/assets/selectandsearchcolumns.png)

### Search options

At the top of the panel, use search options... to quickly find a field by name. This is helpful when many options are available and you want to find one specific item (for example, Event Name or Execution Time) without scanning the full list.

### Show or hide fields

Each item in the list includes a checkbox.

- **Checked** = the field is enabled/visible on the page
- **Unchecked** = the field is hidden from the current layout

Depending on the field, enabling/disabling it may affect:

- the **left filter panel** (which filters are shown), and/or
- the **Events table** (which columns are available/shown)

This helps you reduce clutter and keep only the fields relevant to your current investigation.

### Reorder fields

Each row in the options panel includes a **drag handle** (the dotted grip icon).

Use it to drag items up or down and change the display order.

Reordering can make the page much faster to use, especially during repeated debugging sessions.

### Pagination / incremental loading

If more records exist than are currently shown, use **Load More** to fetch additional rows in the current filtered view.

### Sorting events

Some table headers like event time and date include sorting controls. You can use sorting to quickly answer questions like:

- What are the newest events?
- Which events took the longest?
- When did failures happen in sequence?
